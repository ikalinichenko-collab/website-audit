# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Internal audit tool for gogloby.com. It crawls the audited part of the site, splits every page into zones, and runs three separate layers on each page: **Compliance** (LLM, against the company documents in `sources/`), **GEO** (LLM questions plus code checks) and **SEO** (code only). Every finding names its zone, so the report says where to change something. Node 20+, pnpm, ESM TypeScript run directly with `tsx` (no build step, imports use `.js` suffixes). Needs `OPENAI_API_KEY` and `DATABASE_URL` (Postgres) in `.env`; sign-in with Google needs `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `SESSION_SECRET`, `PUBLIC_URL` (see `.env.example`); locally `docker compose up -d` starts the database (see `.env.example`). Migrations in `migrations/*.sql` run at start of the server and the CLI.

The full design, the decisions behind it and the measured results are in `docs/zones.md` (a local file of the maintainer, not in git: ask for it before changing a layer if it is missing).

The plan for the database, Google sign-in and deploy (stages B and C) and what is already done is in `docs/roadmap.md` (also local, not in git).

## Commands

- `pnpm scan --all` — audit every in-scope URL from the sitemap (scope is the allow-list in `config/settings.json`)
- `pnpm scan <url>...` — audit specific pages (a URL outside the scope is audited with a neutral profile)
- `pnpm scan --limit N` — N URLs spread over the subsections
- `pnpm scan --category <name>... | --subsection <name>...` — audit chosen categories (Services, Company, Resources, Solutions) or subsections (`Resources/Insights` or just `Insights`); repeatable, combines with `--limit N` for a sample
- `pnpm scan ... --force` — ignore the per-layer cache
- `pnpm scan ... --no-compliance --no-geo --no-seo` — turn a layer off (at least one must stay on). An off layer is recorded as not checked (`skipped: true`, shown as "off" in the viewer) and its site-pass part is skipped too
- `pnpm scan ... --model <id>` — model from `llm.models` in `config/settings.json` (default `llm.model`); cost is computed from that model's price
- `pnpm scan ... --no-llm` — skip the LLM calls but keep the layers (SEO and GEO code checks, term list, zones and site pass only)
- `pnpm report [run_id]` — recompute text-fragment links, page rows and counts of a stored run (default: the latest)
- `pnpm build` builds the viewer into `viewer/dist`; `pnpm start` starts the server alone (what a deployment runs). `pnpm app` — build the viewer and start the app server (`src/server.ts`, http://127.0.0.1:8787): run audits, edit documents and settings, browse results. `PORT=...` changes the port
- `pnpm viewer` — Vite dev server for `viewer/` with hot reload (proxies `/api` to the app server on 8787, so start `pnpm server` too)
- `npx tsc --noEmit` and `npx tsc -p viewer/tsconfig.json --noEmit` — type-check (no test runner or linter is configured)
- `scripts/zones-scan.ts`, `seo-scan.ts`, `geo-scan.ts`, `geo-stability.ts`, `compliance-run.ts` — diagnostics over a cache folder of fetched pages; the LLM ones are dry runs unless `--run` is given

## Architecture

`src/cli.ts` calls `runAudit` in `src/audit.ts`:

1. **URLs**: `sitemap.ts` reads the sitemap, `scope.ts` keeps only URLs matching the `scope` allow-list (each rule gives category, subsection and SEO profile). `--limit` samples across subsections.
2. **Fetch and extract**: `fetch.ts` (throttled), `extract.ts` and `html-content.ts` build an `ExtractedPage` (title, meta, canonical, JSON-LD, author, dates, links). Site-wide JSON-LD nodes are found by fingerprint (`schema-fingerprint.ts`, shared by at least `site_wide_schema_share` of pages) and removed from per-page checks.
3. **Zones** (`zones.ts`): the HTML is split into zones (title, meta, og, JSON-LD, H1, blocks `block:<name>#N`, article sections `article:<h2 slug>`, author, shared banner and forms). Every zone has ordered parts (heading, paragraph, list item, table cell, button, link, image with alt state). Header, footer, related content and the job application modal are recorded as skipped.
4. **Shared zones** (banner CTA, forms) differ by template, so each distinct text is a variant (`banner_cta@2`), audited once in the site pass.
5. **SEO** (`seo.ts`, `config/seo.json`): 17 page checks plus regression guards, severity fixed per check in config. `seo-site.ts` adds duplicates, failures collapsed per profile and sitemap hygiene.
6. **GEO**: `geo-code.ts` (`config/geo.json`: home title, trap terms, nearshore in hero, FAQ, em dash, `&`, UK spelling) and `geo-llm.ts` (`prompts/geo-questions.json`, `prompts/geo-llm.md`). The `answer_first` text and the keyword placement come from code. `buyer_ready` answer is derived from its value. `answer_first`, `target_keyword` and `buyer_ready` are `locked` in the file: shown read-only in Settings and refused by the server. Each question has `title`, `severity` (default medium), `needs` (extra data: JSON-LD, og, author and date, links) and `confirm` (a "no" is asked a second time). Answers are cached per question (`qhash` on each answer, taken from the page's report in the latest run), so editing one question asks only that one; a skipped question is asked once more alone. Title, severity and confirm are applied on every run and ask nothing. Code checks carry a severity from `severity` in `config/geo.json`.
7. **Compliance** (`compliance.ts`, `prompts/compliance-zones.md`, `config/compliance.json`): the model returns problems with `locations[{zone_id, quote}]` and a `basis` (contradicts or not in sources); code finds the part, checks the quote and the cited rule, sets severity by category, zone and basis, counts places, adds every occurrence of the banned terms in `config/compliance.json` (`finalizeCompliance`) and derives the page verdict (`deriveAction`). Only the raw model output is cached (`llm_problems`), so editing the term list or severity table does not ask the model again.
8. **Run options** (`AuditOptions`): `layers` (which of the three run), `model`, `subsections` (`Category/Subsection` keys, from `scopeGroups` in `scope.ts`), `limit`, `force`. A run stores `model`, `layers` and the cost (`usageCost` in `config.ts`) in `run.json`; one run uses one model. The layer cache key includes the model, so another model asks again.
9. **Cache**: each LLM layer is keyed by a hash of its payload, prompts, config, sources, model and reasoning (`layerFingerprint` in `config.ts`). The previous answer comes from the latest stored report of the same URL in which the layer actually ran (`previousReport` in `store.ts`), so a run with a layer off does not break the cache of the others. SEO and GEO code checks always rerun.
10. **Site pass**: robots and llms.txt (`site.ts`), shared variants, site-wide schema (one Compliance call each), SEO site checks.
11. **Storage** in Postgres (`src/db.ts`, `src/store.ts`, `migrations/`): table `runs` (status, model, layers, options, `meta`, `site`, `site_sources`), `pages` (`report` jsonb, `entry` for the page list, `html`, `zones`; a row is written as soon as the page is done, so a running audit is readable), `jobs` (status and log; a job or run left `running` by a stopped server becomes `interrupted` at start), `resource_versions` (sources, prompts and config texts with history), `finding_status` (people's decisions: accepted, false positive, fixed; keyed by the stable `fid` of a finding, see `fidOf` in `findings.ts`, so they outlive runs), `kv`. Page findings, the viewer index, `.md` and CSV files are computed from the stored reports when asked for (`findings.ts`, `render.ts`, `run-output.ts`); `quote-fragments.ts` makes text-fragment links to the live page. `results/` is no longer used and is in `.gitignore`.

The company documents the LLM compares against live in `sources/` (`decisions.md` wins over the Fact Sheet, which wins over the Glossary). Code never parses them except `verifyRule`, which checks that a cited rule names a real heading. Changing them changes the layer hashes and triggers LLM reruns.

**App server** (`src/server.ts`, Node `http`, no framework, bound to 127.0.0.1 unless `HOST` is set; `PORT` from the environment): serves `viewer/dist` and a JSON API. **Sign-in** (`src/auth.ts`): Google OIDC with PKCE under `/auth/{login,callback,logout,logged-out}`; the server verifies the ID token (audience, nonce, `email_verified`, `hd` and the email domain equal `ALLOWED_DOMAIN`, default gogloby.com) and sets a signed httpOnly session cookie (7 days). Everything except `/auth/*` needs the session (pages redirect to login, `/api` answers 401); non-GET API calls with a foreign `Origin` are refused. Without `GOOGLE_CLIENT_ID` sign-in is off, and the server refuses to start on any host but loopback. The email is saved in `runs.started_by`, `jobs.started_by`, `resource_versions.author` and `finding_status.set_by`; `GET /api/me` returns it. The app shows people as "Name L." (`users.ts`: table `users` filled from the Google profile name on each request; reads of runs, versions and decisions look the name up, falling back to the part before the @), and names runs in lists as "Name L., dd.mm.yyyy hh:mm" (`runLabel` in the viewer). No roles: every account of the domain has the same rights. Runs: `GET /api/runs`, `/api/runs/:id/{run,index,site,site-findings,site-sources,findings.csv,summary.csv,site.md}`, `/api/runs/:id/pages/:slug[.md|/findings]`, `DELETE /api/runs/:id`. Other endpoints:
- `resources.ts` is the allow-list of editable files (the three `sources/` documents, `prompts/geo-questions.json`, `config/{seo,geo,compliance,settings}.json`, the two prompts). `writeResource` validates the content per file (JSON shape, regex patterns, placeholders, scope profiles), stores the text as a new row of `resource_versions` (30 earlier versions kept) and clears the sources cache. The files in the repo only seed an empty database (`loadResources`, called at start of the server and the CLI, copies them with LF line ends and imports the old `.history/` files); after that the database is the source, and the built-in (`locked`) GEO questions are re-read from `prompts/geo-questions.json` at start. `config.ts` loaders stay synchronous: they read an in-memory snapshot (`resource-store.ts`) that `writeResource` refreshes; diagnostic scripts without a database fall back to the files. Endpoints: `GET/PUT /api/resources/:id`, `.../history`, `.../restore`.
- Finding decisions: `POST /api/findings/status` (`run_id`, `slug` or null for the site pass, `fids`, `status` or null to clear, `note`). `GET /api/runs/:id/pages/:slug/findings` returns `{findings, compare}`: findings carry `status` and `reopened` (marked fixed, found again in a run that started later) and `change: "new"`; `compare` lists what is gone since the previous run of the URL (layers that ran cleanly in both). Counts in the run index and the pages table do not subtract closed findings; the page view does.
- `jobs.ts` runs one audit at a time in the server process (`POST /api/jobs` with pasted URLs, a sample, chosen `subsections`, the whole scope, plus `layers` and `model`; `GET /api/scope` returns the subsection groups with page counts; `GET /api/jobs/:id` returns the log; `POST .../stop`). URLs must be on the site host. `DELETE /api/runs/:id` removes a run. `POST /api/geo-try` (`geo-try.ts`) asks one GEO question on one live page (one model call, nothing saved) for the question editor.

The viewer (`viewer/`, React + react-router + Tailwind) has pages Run, Overview, Pages, Site, Documents (sources) and Settings (GEO questions, SEO, compliance severity, GEO code checks, prompts, general and scope). It reads results through `/api/runs/...` (`viewer/src/data.ts`) and talks to the API through `viewer/src/api.ts`. Its types in `viewer/src/types.ts` mirror `src/run-output.ts`, `src/report-types.ts` and `src/findings.ts`; keep them in sync. Runs made before the zone redesign and before the database are not in it.

## Config

- `config/settings.json`: site URLs, `scope` allow-list, LLM default model, `llm.models` (id, label and price per million input, cached input and output tokens: the choices in the Run page), reasoning effort and concurrency, fetch settings, hidden-content selectors, legacy `page_types` (only used for `ExtractedPage.page_type`).
- `config/seo.json`, `config/geo.json`, `config/compliance.json`: per-layer thresholds, lists and severities.
- Prompts use placeholders such as `{{report_language}}` and `{{questions}}`.
- Gotcha: when editing JSON with regex patterns, backslashes must stay doubled (`\\b`); a single `\b` in JSON is a backspace character and the pattern silently matches nothing.
